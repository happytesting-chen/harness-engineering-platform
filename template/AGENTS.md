## Runtime security model

```
         APPLICATION
              │
      wants to use tool
              │
              ▼
  ┌──────────────────────┐
  │   RuntimeDispatcher  │
  │                      │
  │  tool allowed?       │
  │  capability approved?│
  │  destination allowed?│
  └──────────┬───────────┘
             │ ALLOW
             ▼
            TOOL
             │
             ▼
       External data
             │
             ▼
     CONTENT SCREEN
             │ PASS
             ▼
            LLM
             │
             ▼
      OUTPUT CONTROL
             │
             ▼
      Application / UI
```

**Two rules that govern every capability:**

- **Action rule:** Any governed tool call → RuntimeDispatcher → execution.
- **Data rule:** Any untrusted content → content screening → LLM.

## 4. Identify the Required Security Controls Before Substantial Coding

After the critical requirements are understood, determine which security controls apply to the product before building the corresponding capability.

Use the existing security material as the implementation source of truth, including:

- `security/shared/SECURITY.md`
- `security/shared/active-controls.md` when present and populated
- `security/shared/deny-list.json`
- `security/shared/mcp-allowlist.json`
- `security/shared/permission.py`
- `security/runtime/` and the project's runtime-security tests

Typical capability-to-control mapping includes:

| Product capability | Security consideration |
|---|---|
| Calls tools or performs actions | Action rule: route through `RuntimeDispatcher.execute()` |
| Accesses websites, APIs, or external hosts | Egress allowlist: add host to `mcp-allowlist.json` |
| Uses credentials or secrets | Secret protection: supply via env var only |
| Reads Internet or other untrusted content | Data rule: `screen_input()` on every untrusted source before model context |
| User input reaches model | `screen_input()` on user message — independently of any fetch screening |
| External content (RSS, API, web) reaches model | `screen_input()` on each content item — independently |
| Calls LLM API directly (SDK) | `screen_input()` on all content in messages[]; `screen_result()` on output; RuntimeDispatcher governs what the model proposes to DO, not the SDK call itself |
| Performs sensitive or irreversible actions | Human approval via capability sign-off |
| Returns model output to UI or downstream system | `screen_result()` / `screen_output()` before response leaves the app |

**LLM INPUT BOUNDARY RULE**

`screen_input()` must be called on EVERY untrusted content source **before** it enters the LLM context — not at the fetch site.

Untrusted sources: user input, external API responses, RSS/web content, tool results.

Screening one source does NOT exempt any other.

Ask: *"For each argument passed to the LLM, did it pass screen_input()?"*
NOT: *"Did I screen after fetching?"*

Security is not a separate final phase. Apply the required control while implementing each relevant product capability.

**Never swallow PermissionError silently.** A gate denial must be logged at WARNING level with the original reason. A bare `except Exception` that swallows a PermissionError is a security visibility gap.

## 5. Build the Application and Security Together

For each capability:

```text
Product requirement
        ↓
Determine applicable control
        ↓
Configure the relevant policy
        ↓
Implement the capability through the approved mechanism
        ↓
Add or update verification
```

**RuntimeDispatcher wiring pattern (action rule):**

```python
# Wire once at app startup — all tool calls go through this
from security.runtime.runtime_dispatcher import RuntimeDispatcher

dispatcher = RuntimeDispatcher({"your_tool": your_tool_fn})

# In your handler:
result = dispatcher.execute("your_tool", {"arg": value})
```

The LLM call itself (SDK) does NOT pass through RuntimeDispatcher. RuntimeDispatcher governs what the model proposes to do, not the call that invokes the model.

**Content screening pattern (data rule):**

```python
from security.runtime.runtime_screen import screen_input, InputRejected

try:
    clean_text = screen_input(user_message, source="user")
    clean_article = screen_input(fetched_content, source="rss")
    # Now safe to include in LLM messages[]
except InputRejected as exc:
    # Handle — do NOT re-raise silently
    logger.warning("input DENIED by Gate ①: %s", exc)
```

**PermissionError handling pattern:**

```python
try:
    result = dispatcher.execute("tool", args)
except PermissionError as exc:
    logger.warning("tool DENIED by gate: %s", exc)
    # Handle gracefully — do NOT swallow silently
```

**What to mock in tests:**

```
MOCK (always mock in unit tests)       NEVER MOCK (must stay real)
────────────────────────────────────   ──────────────────────────
Anthropic API / LLM SDK                screen_input()
External HTTP (feeds, APIs)            RuntimeDispatcher.execute()
File I/O on real policy files          permission / allowlist checks
                                       audit.record()
```

If you find yourself mocking a security mechanism, stop. Mock the external service the mechanism wraps, not the mechanism itself.

RuntimeDispatcher tests must use a temp allowlist fixture (see `tests/conftest.py`). Ad-hoc tool names will be denied by the real policy.

Do not create a direct execution path that bypasses the template's security mechanism and plan to secure it later.

## 7. Verify Before Claiming Completion

Product behavior and security enforcement must both be verified.

Run both the harness health check and the product tests:

```bash
./init.sh                                        # harness health check
python3 -m pytest tests/ -q                      # all tests
./init.sh && python3 -m pytest tests/ -q         # composed gate (recommended)
```

**Three mandatory test types for each security control:**

```
MECHANISM test
  Does RuntimeDispatcher / screen_input() behave correctly in isolation?
  → calls the security function directly with valid and invalid cases

WIRING test
  Is the real application code actually calling the security function?
  → calls the real API endpoint or handler
  → asserts RuntimeDispatcher.execute() was invoked (spy or patch the tool fn, not the dispatcher)
  → this test MUST FAIL if the dispatcher is removed or bypassed

CAUSALITY test
  Did the security gate cause the denial — not an unrelated network or parse error?
  → asserts PermissionError specifically (not URLError, not Exception)
  → asserts the denial reason string is gate-specific
```

All three are required per security control. A wiring test that passes when the mechanism is removed is not a wiring test.

**Verification checklist:**

- [ ] Required product functions work
- [ ] Every tool call routes through RuntimeDispatcher.execute() (wiring test)
- [ ] Approved actions are allowed; unapproved actions are denied (causality test)
- [ ] screen_input() is called on every untrusted content source before LLM context
- [ ] screen_input() is called on user input independently of fetch screening
- [ ] Model final output passes output screening before reaching user or downstream system
- [ ] Egress restrictions are enforced (unapproved host denied)
- [ ] Secrets are not passed through unsafe paths
- [ ] Security denials are logged; a PermissionError is not swallowed by a bare `except Exception`
- [ ] For each user-facing capability limitation, the application responds with a clear message
- [ ] The harness health check passes: `./init.sh` exits 0

Do not claim completion merely because the application appears to work.

When the required verification passes:

2. Summarize the security controls applied (which tools, which egress hosts, which screens).
3. Identify unresolved assumptions, gaps, or residual risks.
4. Update `Harness-Best-Practice/progress.md` with the current state and decisions.
5. Present evidence for capability approval:

```
CAPABILITY APPROVAL REQUIRED

This phase enables:
  ✓ <tool_name> — <purpose>
  ✓ outbound connection to <host>

Purpose: <why these are needed>

```

6. Wait for the developer to run `python3 security/shared/signoff.py <phase-id>`.

The coding assistant must not self-promote phases that require human approval. The developer runs `signoff.py` — Claude cannot write to `mcp-allowlist.json`.

# Working Rules

- **WIP=1** — One task at a time. Finish or park before starting another.
- **Verify before claiming done** — Run the required verification command. Exit 0 = done only when the command is intended as the completion gate.
- **Update progress.md** — Record what was done, decisions, and next steps before session end.
- **Stay in scope** — Work only within the agreed requirements and active phase.
- **Do not guess critical requirements** — Ask the developer.
- **Leave clean state** — No temporary files, broken tests, or uncommitted debug code.
- **Do not bypass security controls** — Product code must use the intended governed path.
- **Never swallow PermissionError** — A gate denial must be logged at WARNING level. User-facing messages may be generic, but the application log and audit trail must record the security event.

# Hard Constraints

Hard-blocked patterns (see `security/shared/deny-list.json`): `rm -rf` on filesystem roots, `mkfs`, `> /dev/`, fork bombs, `shutdown`, `reboot`, and shell writes/edits to any file in `security/`, `security/runtime/core/`, or `.claude/settings.json`.

- Enforcement is mechanical — `security/shared/permission.py` evaluates governed tool calls.
- Four gates in order: protected-paths → deny-list → phase-gate → egress (fail-closed, first denial wins).
- The agent CANNOT bypass, modify, or disable the permission gate.
- Phase transitions require human sign-off; the agent cannot self-promote phases.
- Patterns in `security/shared/deny-list.json` are blocked unconditionally.
- Security files existing in the repository do not by themselves protect the deployed application; the application must route the relevant runtime actions and data through the security mechanisms defined by the template.

# Escalation

- **Scope ambiguity:** Re-read `Harness-Best-Practice/feature_list.json` and `Context/`; ask the developer if the ambiguity remains.
- **Tool not available:** Check `security/shared/mcp-allowlist.json`; do not bypass the permission mechanism.
- **Repeated failures (3+):** Update `Harness-Best-Practice/progress.md` and flag the issue for human review.
- **Permission denied:** Do not retry or bypass the denial. Record it in `Harness-Best-Practice/progress.md` and surface it to the developer.
- **Security denial hidden as empty result:** Distinguish `PermissionError` from network/parse errors. Log the denial; do not let it silently become "no results".
